## 明天从这里接续

Owner：根 Codex；执行者使用目标机现有 CLI，优先续接原会话。命令与恢复入口先读[436 运行说明](../../docs/paperclip-436.md)，不要把历史 `bootstrap.sh` 当成通用安装器。现有 `lark-cm436` 与 watchdog 含 436 专用配置，不能原样覆盖其他机器。

1. **先做一台新增主机的完整真实任务，再复制到下一台。** 在该主机任务的现有 SpecMesh 材料中写清有效 `cm` 入口、cwd/服务 owner、模型配置来源、原 bot 身份、有效 cron/timer、恢复入口。程序可复用；账号、公司/Agent ID、权限与启用状态逐机保留。采用 CapMesh PIT-005 与 Obsidian `Wiki/工具链与认证体系` 的分层经验；不分发整套 436 私有配置。
2. **派发一次，交接一次。** 主 Agent 带上已选 Paperclip 方向、可复用能力、本次缺口、保留项和交付位置；执行者先说明准备动哪里。使用已经可用的派发/结果路径，不把尚未实现的方向核对机制当成安全门。派发后结束协调模型推理，由执行系统等待；结果或异常到达时再判断，不持续调用模型盯进度。
3. **切换消费者，用一件实际成果验收后收口。** 启动新消费者前先停旧消费者，避免同 bot 双收件；核对新入口确实执行目标任务、成果对应本轮、主 Agent 独立判断，并回到原飞书会话。失败时先停新消费者，再恢复旧入口；保留 cron 和回退材料。正文解析、附件、群聊分别按真实任务验收，不互相代替。运维无异常静默；按任务发送最终结果、异常或真正需要用户判断的分歧。

收尾更新该主机 `progress.md`，及时提交/推送有效工作；CM 当前引用用现有 `cm-closeout check` / `cm-closeout sync` 接到 CapMesh。正常结果不让多台服务器重复发送同一份运维消息。不增加 GitHub Actions、自动 hook 或新调度服务。
