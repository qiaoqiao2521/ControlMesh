# CM 基于 Paperclip 的改进方向

## Goal
将 CM 后续方向收敛为 Paperclip 基础上的改进版，优先复用原生任务、依赖、派发和唤醒，保留 CM 有实际价值的飞书/群聊与交付能力。

## User confirmation
2026-10-01 再确认：CM 是工作流概念与薄适配层，本质运行 Paperclip。仓库入口必须开头说明，新 Agent 不应再将 CM 当独立运行时建设。

2026-09-30 用户在完成真实 CLI 实验后明确要求“记录在 cm specmesh”，并表示 CM 以后成为该仓库的改进版。此处“该仓库”指 Paperclip。该确认取代 Orca 作为默认未来底座的选择；旧实现与验收资料保留。

同日后续明确：CM 直接复用/clone Paperclip，保持上游源码不动，最多加入自己的薄编排层。执行前方向核对先记录；若无法优雅复用，可以不加入。这次确认不要求立即 clone、实现或部署。

## Requirements
- 纯 CLI 是必需路径；Codex 协调真实 AGY、ZCode、CBC 等现有 CLI。
- 派发后协调模型结束本轮推理，由执行系统等待；结果交齐后原生事件唤醒 Codex 独立审批。
- SpecMesh 交接当前目标、约束、结果和证据；尽量续接原会话。
- 任务交接完成、模型进程成功、产品通过验收分别判断；允许有依据拒绝与停止。
- 用户只收到有意义的结果、异常或需判断的分歧；不增加多份重复运维消息。

## Non-goals
初始方向记录不创建新 fork，也不自动迁移生产 CM；后续获准的本地飞书安装与服务器试验见[canary](../paperclip-feishu-canary/task_plan.md)。保留 Orca/TS 候选和现有生产入口，不另造通用调度器。

## 执行前方向核对：已记录，待选用

真实问题：用户转述的 436 部署复盘中，Agent 已知道新方向，却继续修改旧 Python CM、验证 `/status`；当时并未部署 Paperclip。局部修复成功不能代替目标推进。此处记录用户提供的案例，不冒充本轮服务器核验。

需求：主 Agent 将已选方向、可复用的已验收链路、本次缺口、必须保留的资产及其来源带入交接。执行者先说明准备修改哪里、如何推进当前目标；由主 Agent 判断后再实施，完成后仍独立验收。正常等待不持续调用模型，不把日常判断交回用户。

候选最小接法（尚未实施）：
1. 复用现有派发入口与 SpecMesh 任务材料，先交短提案并结束本轮；提案阶段需有经过验证的修改权限限制。
2. 用 Paperclip 原生审查参与者/计划版本/事件唤醒表达批准或退回；批准绑定具体提案版本，内容改变后旧批准不得继续放行。
3. 获准后才经已有接口启动有写权限的实施阶段，尽量续接原会话；不提前启动实施进程再靠提示词让它等待。不为这个需求固定增加 Agent 或服务。

采用条件：在选定 CLI 与真实入口上证明“提出修旧 CM → 审查退回 → 旧服务和代码尚未改变”，再证明正确提案获准后能够实施、等待和交付。原生状态转换通过不能代替这条端到端验收。

停止条件：需要修改 Paperclip 上游源码、复制其状态机/另建调度器、显著增加维护或上下文成本，或无法清楚实现批准前的修改限制时，保留需求，不加入。此项属于 Agent 运行时编排，不放进仓库收尾 CLI、GitHub Actions 或全仓强制流程。
